# Архитектура Darmen New Wave

## Цель

Не копировать функции ERP и не заменять 1С. Обеспечить единый операционный контур: клиентское досье → заявки → проверка условий → склад → рейс → доставка → документы → контроль оплаты.

### Логические системы

1. **Учётная система 1С** — юридические контрагенты, договоры, номенклатура, цены, учётные остатки, реализации, возвраты, оплаты и дебиторка (источник истины).
2. **Darmen New Wave frontend** — пользовательские формы, статусы, маршруты и бизнес-дашборды.
3. **Backend Distribution (будущий)** — серверная авторизация, RBAC, API, доменные транзакции, защита файлов, журнал событий, устойчивый обмен.
4. **Интеграционный адаптер 1С (будущий)** — очередь обмена, курсоры, идемпотентность, ошибки, наблюдаемость.
5. **Существующее планшетное приложение (неизвестно)** — интегрировать, а не заменять до обследования его возможностей.

## Базовые сущности

- `Customer`: юридический контрагент, БИН, условия оплаты, лимит, статус.
- `Outlet`: физическая точка доставки с адресом и назначенным представителем. Один `Customer` → несколько `Outlet`.
- `Visit`: плановый визит торгового представителя, дата, цель, статус, результат и ссылка на торговую точку.
- `Product / Warehouse / Stock`: номенклатура, склады, фактический и резервный остаток.
- `Order / OrderItem`: заявка, позиции, дата доставки, этапы, источники.
- `Debt`: документ задолженности, дата оплаты, открытый баланс. По юридическому контрагенту.
- `Consignment`: отдельная передача товара под реализацию, отчёт о проданном и возврате; не равна обычной дебиторке.
- `DeliveryRoute / RouteStop`: рейс, водитель, автомобиль, последовательность магазинов, назначенные заказы, исход.
- `DocumentRecord`: метаданные и будущая ссылка на защищённое файловое хранилище.
- `Activity`: журнал действий с автором и временной меткой.

## Основные бизнес-правила

- `Order`: new → confirmed → picking → ready → in_route → delivered/partial. До отгрузки возможна отмена.
- Подтверждение заказа проверяет статус клиента, кредитный лимит (долги + активные подтверждённые, ещё не выставленные в реализацию заказы) и доступный остаток склада. В демо резерв создаётся локально; реальные учётные движения возможны только в согласованной интеграции.
- Рейс собирается из заказов `ready` на одну дату и проверяет расчётный вес против грузоподъёмности.
- Доставка `partial/failed` не может автоматически списывать полное количество или формировать полноценный бухгалтерский результат. Резерв таких заказов остаётся до сверки с 1С; инциденты отображаются на дашборде.
- Задолженность хранится на уровне `Customer / Contract`, доставка относится к `Outlet`. В дальнейшем нужны договоры, разные условия по договорам и отдельные типы реализации.
- В промышленном backend обязательно: транзакционные обновления, блокировки резервов, проверка статусов, область видимости пользователя и аудит операций.

## Что намеренно не реализовано

- Реальная 1С-интеграция, авторизация и серверный RBAC.
- Реальная файловая загрузка/выдача документов, подписи, QR-подтверждения.
- Полная модель разнотипных складов, лотов, партий, возвратов и налогового учёта.
- Оптимизация маршрута по расстояниям, пробкам и временным окнам.
- Мобильный офлайн-режим, синхронизация планшетов, push-уведомления.
- Реальные платёжные проводки, электронные счета и юридические претензии.
- Multi-tenant изоляция для нескольких дистрибьюторов.

## Слои

- `src/types/domain.ts` — строгие контракты UI.
- `src/utils/domain.ts` — чистые расчёты и разрешённые переходы.
- `src/access.ts` — только UX-уровень разрешений (не безопасность).
- `src/data/seed.ts` — строго фиктивные демоданные.
- `src/stores/distribution.ts` — операции браузерной демонстрации.
- `src/components/ui/` — базовые UI-примитивы и формы.
- `src/layouts` и `src/pages` — представление.
- Будущий `src/api/` — адаптер к backend, после подтверждения протокола.

Роли и разграничение бизнес-действий на backend — отдельный проектный вопрос, который нельзя заменить проверками на frontend.

## Обмен возвратами и состоянием рейса

Контур frontend отражает операции по схеме: заказ → резерв товара → рейс →
ручное прибытие → результат доставки → отчёт экипажа о расхождениях →
подтверждение кладовщика → обновление тестовых остатков. Реальные первичные
документы, долгосрочные вложения, подписи, недостачи/списания, API и транзакции
в 1С пока отсутствуют. Записи нельзя использовать для бухгалтерского баланса.
